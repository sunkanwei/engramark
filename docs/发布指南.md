# 维护者发布指南

**[English](release-guide.md) | [简体中文](发布指南.md)**

本文只面向维护者，说明什么时候需要发布新版本，以及如何构建、验证和公开 Engramark。使用者安装、升级和卸载见[安装指南](安装指南.md)，测试命令的完整说明见[测试与验收](测试与验收.md)。

## 先区分四件事

| 动作 | 含义 | 是否产生公开版本 |
|---|---|---:|
| Git 提交 | 在本地记录一组改动 | 否 |
| 推送分支 | 把提交同步到远端仓库 | 否 |
| 推送版本标签 | 触发四平台发布流水线 | 只生成草稿 |
| 公开 GitHub Release | 发布版本说明和下载资产 | 是 |

普通提交不等于发布。只有版本号、标签、自动化验证和公开 Release 全部完成，使用者才会看到一个新的可下载版本。

## 什么时候需要发布

| 改动 | 通常的处理 |
|---|---|
| 只修改代码注释、内部重构、开发者文档或不影响使用的文字 | 不发布 |
| 修复会影响使用者的缺陷、安全、兼容性或数据可靠性问题 | 发布补丁版本 |
| 修复已公开安装说明中会导致安装或使用失败的错误 | 发布补丁版本 |
| 新增向后兼容的用户功能或平台支持 | 发布次版本 |
| 公开行为发生不兼容变化 | 发布主版本 |

版本号遵循语义化原则。不要为了制造“新版本”而发布没有实际用户价值的空版本。

准备发布前，先向项目负责人说明建议版本号、发布原因和面向使用者的变化。没有明确授权时，不得推送版本标签或公开 Release。

## 发布模型与目标

Engramark 为每个平台构建一个原生程序：

| 目标参数 | 平台 | 归档格式 |
|---|---|---|
| `macos-arm64` | macOS Apple Silicon | `.tar.gz` |
| `macos-x86_64` | macOS Intel | `.tar.gz` |
| `linux-x86_64` | Linux x86_64 | `.tar.gz` |
| `windows-x86_64` | Windows x86_64 | `.zip` |

四个平台必须在各自原生 runner 上完成构建和运行验证。交叉编译不能代替能力自检、完整测试和安装生命周期。

发布包只包含可替换程序、Codex/OpenCode 适配器、默认配置、文档、许可证和供应链元数据，不包含真实记忆、本机索引或持久状态。

## 发布流程总览

```mermaid
flowchart LR
    A["准备版本"] --> B["本地完整验收"]
    B --> C["提交并推送主分支"]
    C --> D["创建并推送 v* 标签"]
    D --> E["四平台构建与复验"]
    E --> F["生成未公开草稿"]
    F --> G["人工检查资产与证明"]
    G --> H["公开 Release"]
    H --> I["发布后复核"]
```

## 1. 准备版本

发布前确认：

- [ ] 根目录 `VERSION` 与 `rust/Cargo.toml` 的版本一致；
- [ ] 目标标签为 `v<版本>`；
- [ ] 工作区只包含预期改动，不含真实记忆、凭据或本机产物；
- [ ] 面向用户的行为、支持边界和中英文文档已经同步；
- [ ] 金样变化经过明确评审，并同时更新实现、清单与说明；
- [ ] 建议版本号和发布原因已经获得授权。

## 2. 本地构建与验收

只构建当前机器能够原生运行的目标：

```sh
python3 packaging/build_release.py --target <当前原生目标>
```

构建器使用锁定依赖完成 release 构建和能力自检，然后生成：

```text
dist/engramark-<版本>-<目标>.tar.gz
dist/engramark-<版本>-windows-x86_64.zip
dist/checksums.txt
```

每个候选包包含：

- 原生 `engramark` 或 `engramark.exe`；
- 默认配置、宿主适配器和中英文文档；
- `SBOM.json`；
- Rust 依赖与 Unicode 数据的上游许可证；
- `MANIFEST.tsv`，记录逐文件类型、大小与 SHA-256。

发布前至少完成：

```sh
python3 tests/run.py
python3 tests/test_repository_privacy.py
python3 tests/test_documentation.py
ENGRAMARK_SCALE_CARDS=10006 python3 tests/test_retrieval_scale.py
python3 packaging/build_release.py --target <当前原生目标>
python3 tests/test_install_lifecycle.py
```

格式、静态检查和供应链命令见[本地完整门禁](测试与验收.md#本地完整门禁)。

生命周期会在隔离用户目录中验证危险归档拒绝、安装、宿主接入、查找、写入、备份、升级重装、卸载，以及卸载后记忆完整保留。

Linux 产物在 Ubuntu 22.04 构建，并拒绝高于 glibc 2.35 的符号需求。macOS 产物声明 13.0 deployment target；该声明不是在具体 macOS 版本完成原生运行的证据。

## 3. 推送版本标签

只有主分支目标提交、必要测试和 CI 全部通过，并且已经获得发布授权时，才创建与 `VERSION` 一致的标签：

```sh
version=$(cat VERSION)
git tag -a "v$version" -m "Engramark v$version"
git push origin "v$version"
```

不要改写已经公开的标签，也不要原地替换已经证明的发布资产。公开版本发现问题时，保留旧版本并创建新的补丁版本。

## 4. 等待 GitHub 发布候选

标签触发 GitHub Actions 后，流水线会：

1. 运行静态、文档、隐私和供应链门禁；
2. 在四个原生 runner 上运行完整测试、能力自检、打包和安装生命周期；
3. 在较新系统上复验同一候选包；
4. 汇总统一 `checksums.txt`；
5. 为产物生成 GitHub 构建来源证明；
6. 创建未公开的 GitHub Release 草稿。

自动化不会直接公开版本。由临时 runner 或网络问题导致的失败可以复跑同一作业；如果修复需要改变候选内容，则不得移动原标签，必须提升版本并创建新标签。不能跳过失败作业，也不能把草稿描述成已经发布。

## 5. 检查并公开草稿

公开前确认：

- [ ] 四个平台构建全部通过；
- [ ] 四个平台兼容性复验全部通过；
- [ ] Release 包含 4 个原生产物和统一 `checksums.txt`；
- [ ] GitHub 构建来源证明可见；
- [ ] 文件名、标签、`VERSION` 和 Cargo 包版本一致；
- [ ] Release 说明准确概括使用者可感知的变化；
- [ ] 未签名与系统警告边界仍然如实说明。

当前分发使用三层完整性信息：

- 外层 `checksums.txt` 检查下载内容；
- 包内 `MANIFEST.tsv` 检查展开后的每个文件；
- GitHub 构建来源证明确认产物来自本仓库工作流。

这些措施不等同于操作系统代码签名。当前公开包没有 Apple Developer ID 签名、公证或 Windows 代码签名，用户仍可能看到来源或未知发布者警告。签名流程真正完成前，不得把校验和或来源证明描述成代码签名。

## 6. 发布后复核

公开 Release 后确认：

- [ ] 最新版本页面取得 4 个正确平台包和统一校验清单；
- [ ] 安装脚本可以解析资产名称并选择当前平台；
- [ ] GitHub 构建来源证明可以公开访问；
- [ ] README 与安装指南中的命令仍然有效；
- [ ] 新版本被标记为 Latest；
- [ ] `main` 上没有被遗漏的发布修复。

Engramark 本体采用 MIT 许可证；每个候选包还必须携带依赖 SBOM 和上游许可证集合。
